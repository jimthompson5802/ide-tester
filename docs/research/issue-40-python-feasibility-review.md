Terminal text access is a smaller uncertainty now. The [driver implementation](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/src/vs/workbench/services/driver/browser/driver.ts#L191) returns `string[]` from `xterm.buffer.active`; it does not return command IDs, raw shell-integration control sequences, process IDs, or exit codes. The [Playwright adapter](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/test/automation/src/playwrightDriver.ts#L868) calls this same window driver. The [desktop window](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/src/vs/workbench/electron-browser/window.ts#L709) registers the driver conditionally. Read-only inspection of the installed `out/vs/workbench/workbench.desktop.main.js` found the corresponding method and its xterm-buffer implementation. This proves packaged code presence, not operational availability. The current [standalone workbench](../../smoke/src/workbench.ts) exposes only two driver methods; phase 2 would still need a narrow capability check and bounded read method.

Successful completion has a concrete candidate rather than an unspecified future API. The upstream [process-based shell-integration tests](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/test/smoke/src/areas/terminal/terminal-shellIntegration.test.ts#L25) choose bash on macOS/Linux, enable integration, run `echo` or `false`, and assert success/error decorations. The same file separately labels its later tests as simulated terminal writes; those simulated tests do not prove real shell behavior. The [decoration state implementation](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/src/vs/workbench/contrib/terminal/browser/xterm/decorationStyles.ts#L158) distinguishes unknown exit status from zero; success is not merely the absence of an error. The [terminal helper](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/test/automation/src/terminal.ts#L16) supplies the success/error/incomplete CSS selectors.

Proposed refinement for P1-T02/P1-T03: capture the owned target terminal and decoration baseline, invoke Python Run once, require fresh current-run output and independent JSON, then observe a new success decoration associated with the script command. Interpreter activation or other startup commands may also produce successful decorations; a global success-count increment alone is insufficient. A transient running decoration may be too brief for this small program, so do not require catching that intermediate state if command correlation and final zero-exit observation are otherwise proven. Verify the installed build's behavior before treating this as an accepted contract. Do not inject terminal escape sequences or run Python directly to manufacture completion evidence.

Shell configuration needs explicit treatment. The [injection implementation](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/src/vs/platform/terminal/node/terminalEnvironment.ts#L143) accepts empty bash arguments or recognized login arguments and rejects unsupported argument combinations. The [bash integration script](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/src/vs/workbench/contrib/terminal/common/scripts/shellIntegration-bash.sh#L30) reads `~/.bashrc` for a non-login injected shell, whereas login setup can read `/etc/profile` and user profile files. A candidate to review for P1-T01 is an explicit `/bin/bash` terminal profile with an empty argument list and a disposable owned HOME containing no startup files; verify the effective terminal HOME rather than assuming the launch environment survives unchanged. Do not assume `--norc`/`--noprofile` are compatible substitutes. Candidate settings include `terminal.integrated.shellIntegration.enabled: true`, decorations enabled, tabs visible, and persistent terminal sessions disabled; these are proposals until the full profile/environment procedure is reviewed. The upstream [settings helper](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/test/smoke/src/areas/terminal/terminal-helpers.ts#L9) also disables GPU acceleration for trace inspection; that setting is optional for this suite, not a new dependency.

Extension installation remains less certain. The [extension helper](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/test/automation/src/extensions.ts#L23) uses `@id:` and `data-extension-id`, then checks Uninstall and enabled Disable controls. Its [calling smoke test](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/test/smoke/src/areas/extensions/extensions.test.ts#L19) is `it.skip` and installs `ms-vscode.vscode-smoketest-check`. The helper retries installation; retain this plan's zero-retry policy instead. Do not copy the upstream settings-clearing teardown into a persistent profile. There is no inspected Python extension implementation here from which to establish interpreter-picker labels, current dependencies, environment-activation settings, or installation side effects.

Cleanup remains a gate. The upstream [Kill All branch](https://github.com/microsoft/vscode/blob/68d4ae5bd0e97974ee16dda2053feb95c05371d1/test/automation/src/terminal.ts#L106) deliberately continues after a timeout. The local [runner](../../smoke/src/runner.ts) waits for the main owned application process to exit; [finishRun](../../smoke/src/resources.ts) preserves resources/reservation on a reported shutdown error. Neither inspection demonstrates that Python terminal descendants have exited. P1 must establish that guarantee before relying on existing cleanup unchanged.

Recommended next step: refine P1-T01 around the terminal-buffer capability check, the correlated success-decoration approach, and a shell profile compatible with integration. Keep Python-specific UI/install, real completion correlation, deadlines/cancellation, and descendant shutdown as explicit walkthrough checks. No phase checkboxes should be marked complete from this review. Source inspection and installed-bundle presence checks were performed; no runtime tests or GUI checks were run.

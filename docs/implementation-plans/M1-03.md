## Agreed policy and implementation approach

The developer accepted Q1–Q8 and Q10–Q12 during plan review and rejected Q9's intermediate developer checkpoint. The agreed decisions are:

- Protect against accidental misuse, unsafe paths, symlinks, and detectable directory replacement. Deliberate interference by a hostile same-user process is outside the supported threat boundary.
- Fix the root at `<actual-source-checkout>/workspaces/`, independently of cwd/config location; accept the writable-source-checkout requirement. Keep reports cwd-relative.
- Accept optional `harness.workspace.retain_on_failure`, defaulting to `false`. Retention covers all known nonpassing outcomes after creation, including blocked operations, interruption, and unimplemented operations. Failures discovered after successful deletion cannot restore the workspace; report its actual disposition.
- Exercise creation and finalization through admitted public runs even while IDE operations remain unimplemented.
- Require a valid purpose marker before using an existing workspace root. Do not adopt unmarked roots or their children automatically.
- Permit safe unlinking of nested symbolic links while preserving their targets. Refuse cleanup if that safety cannot be established; linked or replaced workspace roots remain unsafe.
- Leave abandoned-resource recovery and marker repair manual. No automatic sweep, adoption, or repair belongs to this story.
- Write a small workspace manifest before cleanup and record the final disposition in the summary; successfully updated artifacts must agree. Exclude file contents.
- Use one deterministic `example.py` containing `message = "original fixture"` plus a trailing newline.
- Use **one implementation phase**, with no intermediate developer checkpoint between filesystem qualification and integration. Keep safety tests as prerequisites for dependent integration and retain final M1-03/Slice 1 validation. These design decisions and permission to revise this plan do not authorize implementation.

Qualify deletion mechanisms early in the single phase, then integrate only after their checks pass. If evidence invalidates the agreed safety approach, stop for guidance under the scope-change controls below. There is no routine pause for developer approval between these task groups.

The following module names and mechanisms remain implementation proposals, constrained by the agreed behavior:

1. Derive the fixed workspace root from the actual editable-source checkout, independently of cwd and YAML location. Keep reports at the existing cwd-relative location. This limits deletion to one already ignored root and avoids an arbitrary cleanup-path API. Resolve the trusted checkout anchor once; check components below it without following symlinks. OS aliases in a canonical temporary test anchor must not produce misleading failures.
2. Create the root exclusively when absent, with a small versioned purpose marker `.ide-smoke-workspaces.json`. Existing roots require the exact valid marker and real directories; never adopt an unmarked directory or overwrite a marker. Partial initialization must remain preserved and reported, with no broad repair/rollback. Root ownership permits creating children, never deleting the whole root or adopting its existing children.
3. Create a fresh direct child with an exclusive filesystem operation and a run-correlated generated name. A collision must never reuse or overwrite a directory. Return a proposed `WorkspaceHandle` containing run ID, root/child identities, workspace path, target path, and initial fixture digest. Cleanup accepts a handle created by this manager for this run, not an arbitrary user path or an on-disk marker alone. Persisted metadata does not authorize future cleanup of old runs.
4. Write one fixed `example.py` using known UTF-8 bytes, agreed `message = "original fixture"\n`. Define the bytes/name in the workspace module, without package-data machinery or another dependency. The file need not execute. Later IDE-edit stories can consume the handle and independently verify disk changes. Read back the newly created fixture before declaring creation complete.
5. Require strict descendant containment, parent and child identity agreement, no overlap with home roots, persistent profiles, everyday IDE data, installation, source/configuration/report resources, and no traversal or case-alias escape. The workspace root is the sole permitted writable subtree of the checkout for this lifecycle; protect other checkout content. Reject unsafe symlink components and wrong kinds. Compare both canonical paths and existing filesystem identities where appropriate. Never recurse into the persistent profile or enumerate its contents.
6. Revalidate immediately before cleanup. Qualify Python 3.12's descriptor-relative and symlink-resistant stdlib deletion support on the existing macOS host. Do not rely on `resolve()` plus unchecked `rmtree()`. Refuse deletion on identity changes, unsafe links in root components, unsafe entries, unsupported safety primitives, or indeterminate inspection; preserve the resource and emit a controlled cleanup error. Nested symbolic links may be safely unlinked but must never be followed; qualify this behavior before integration. No native helper or dependency installation is authorized.
7. Keep retention minimal: retain the entire synthetic workspace in place when configured and the run is nonpassing; no snapshot/copy subsystem, prune command, or automatic stale-run sweep. Never reuse a retained workspace. Metadata reports its location and disposition; file contents, arbitrary filenames, environment values, and exception text must not enter diagnostics.

A purpose marker records intent; it does not prove every child is disposable. Identity checks and qualified deletion reduce targeting risk but do not promise safety against a hostile same-user process continually replacing directories or mount points. The implementation must test observable replacement cases and stop if it cannot establish the required protection of unrelated files within the agreed threat boundary.

## Scope and approval boundaries

Check prerequisites before GUI tests so environmental problems do not appear as IDE regressions. Cover configured-executable runnability, the intended macOS graphical session, required automation permissions, dedicated-profile paths, expected Copilot extension presence, and a human-readable one-time setup guide. Demonstrate successful preflight and at least one controlled or simulated blocked preflight.

Use the existing macOS login with exclusive desktop use during runs. Preserve the dedicated authenticated profile. Authentication and OS permission grants are manual. No passwords, MFA automation, credential extraction, authenticated-profile copying, or credential-store inspection is permitted.

M1-03 owns disposable-workspace creation and cleanup. M1-04 owns operational IDE launch, process/window identification, readiness, and shutdown; M1-06 owns opening Chat and observing sign-in requirements. This story does not implement those operations, send Copilot requests, or resume historical M1-00 probes. Windows, IntelliJ, screenshot infrastructure, release monitoring, scheduling, and extra adapter frameworks remain outside scope.

The two phases below separate unqualified readiness mechanisms from production integration. Phase 2 is conditional on Phase 1 evidence and developer validation. Story acceptance does not approve Slice 1: M1-01, M1-02, and M1-03 must be reviewed together before M1-04. No phase of this plan advances that gate automatically.

## Technical approach and decisions to qualify

### Shared preflight and platform boundary

Add a small shared preflight entry point, proposed at `src/ide_smoke/preflight.py`, called after strict configuration validation and before any IDE operations. Incorporate basic resource availability into this stage so a missing executable/profile does not prevent independent session/permission checks from reporting their findings. Isolate macOS framework imports and observations in proposed `src/ide_smoke/platforms/macos/preflight.py`. Keep configuration, classification, reporting, and tests independent of platform libraries. Use a small injectable observation boundary for tests; no general plugin registry or speculative lifecycle contracts are needed.

Check sequentially in a fixed order: resolved executable and runnability; profile isolation/layout and required setting; session and permissions; expected extension metadata. Continue all independent safe checks after a block/error. Skip a dependent check with its input's originating reason, such as extension inventory when the selected installation cannot be established; do not create a general dependency engine. Record every finding, duration, and unperformed check. Aggregate preflight errors before blocks; for findings of equal severity, choose the first in this fixed order as the primary reason. Use that primary reason for dependent T01–T05 skips while preserving all findings in the report. No IDE operations follow any preflight block/error. Preflight is a run prerequisite, not a sixth smoke test and not evidence that T01–T05 passed.

Use the existing startup-timeout value as the total preflight deadline. Future T01 receives its own full startup budget; time spent in preflight does not consume it. External commands receive the remaining preflight deadline, bounded output, and process cleanup; repeated polling must also respect that deadline. When the deadline is exhausted, preserve completed findings, report the timeout as `HARNESS ERROR`, and identify checks not performed. Do not assume passing a timeout into a function bounds blocking native calls: qualify the selected calls and isolate any potentially blocking probe with bounded termination. Avoid a general timeout framework. Unexpected exceptions, malformed observations, and unexplained timeouts retain uncertainty as `HARNESS ERROR`. If qualification demonstrates a need for a separate timeout setting, present a plan revision before adding it.

### Executable and profile identity

Reuse config path rules and preserve the M1-01 directory-skipping fix and its regression tests. M1-02 extends runtime lookup for bare commands to skip both directories and nonexecutable files, selecting and retaining the first executable regular file. Indeterminate access remains an error rather than being silently skipped. If no executable is found, retain meaningful observed wrong-kind/nonexecutable diagnostics rather than describing rejected candidates as absent. An explicitly configured nonexecutable path is `BLOCKED`, with no PATH fallback. If the existence-only `check_resources` helper remains, preserve its narrow contract and tests; the run's preflight must use the qualified executable-selection policy instead of treating that helper's first regular file as the final target.

Validate the selected executable as the official VS Code app or official CLI, and correlate CLI symlinks with their associated installation. Do not continue searching for another installation if that selected executable is an unsupported wrapper, another distribution, or cannot be identified reliably. Support configurable installation locations without pinning paths or versions to today's observations; record which combination was actually qualified. Unsupported launch forms/layouts are actionable `HARNESS ERROR` findings. Existence and executable permission alone do not prove the program can run: qualify a bounded, non-GUI invocation tied to the configured installation. A short-lived CLI/version subprocess is permitted, but the check must not launch an editor instance/window or attach to an existing editor. If a companion bundled CLI is necessary for an app executable, establish its relationship to that exact app.

The proposed convention is `profile_root/user-data` plus `profile_root/extensions`, matching the spike's separation. Phase 1 must confirm it before Phase 2 documents it as supported behavior. Require a small nonsecret setup-owned dedication marker; its exact filename/format is a routine implementation choice. It records the developer's intended use, without proving that arbitrary profile contents are safe. Reject known everyday VS Code directories and unsafe symlink/overlap cases even if a marker exists. The guide may explicitly adopt the existing dedicated M1-00 profile after validating paths/layout and manually adding the marker. Do not migrate, copy, or recreate it, or require another sign-in solely to add the marker. Manual reauthentication is needed only when the existing session requires it. Preflight validates access without changing settings, creating/repairing directories or markers, or probing credential data. The marker never authorizes deleting the profile.

Check the allowlisted effective setting `editor.accessibilitySupport`: the qualified path requires `on`. A confirmed incompatible effective value blocks with manual remediation; an absent setting alone must not be mistaken for a known effective value. If the effective value cannot be established reliably, record `HARNESS ERROR`. Phase 1 must qualify a narrow settings check, accounting for the supported settings representation and relevant precedence, without dumping unrelated settings or introducing an IDE interaction probe. Preflight never changes the setting.

### Session and permissions

Qualify nonprompting checks for the current user's intended foreground, unlocked graphical session and the capabilities needed by the established Accessibility/keyboard path. Consult primary platform documentation during execution, and record the exact check, execution context, observation, and limitation. Treat a known unavailable/locked session or denied required capability as `BLOCKED`, with manual remediation. An unsupported or inconclusive check is `HARNESS ERROR`, not a product failure or a permission success.

The developer clarified the graphical-session acceptance boundary: documented session and permission observations establish a snapshot of prerequisite readiness; actual IDE/window interaction remains T01 evidence. Do not promote `frontmostApplication() != None` or Accessibility trust alone into proof that an IDE window can be driven. Phase 1 must qualify the combination of passive checks and document each check's limits. M1-02 adds no owned-window interaction probe or IDE lifecycle adapter and performs no unrelated app/window interaction. If passive observations cannot reliably establish even this prerequisite snapshot, record the gap and stop for a plan revision; do not claim readiness or expand into GUI testing automatically.

Check only capabilities needed by the chosen path. Do not require Apple Events Automation or Screen Recording merely because the draft proposal lists them; document them as unused/unverified when appropriate. Do not prompt for permissions or grant them automatically. Exclusive desktop use remains a documented operating condition confirmed during setup/qualification; the advisory run lock excludes cooperating harness invocations, not human activity or other apps.

### Extension presence and authentication

Identify `github.copilot-chat` from allowlisted manifest fields in the selected app's bundled extensions and the dedicated extensions directory, accounting for the installed build's selection/override behavior where it affects the result. Record identifier/version/source without dumping manifests or enumerating unrelated extension/account data. A complete, successful search with no expected extension is `BLOCKED` for missing extension; unreadable or ambiguous inventory is `HARNESS ERROR`. Known disabled/unavailable state must not be described as usable. If metadata establishes presence only, state that limit; activation and live Chat availability are later UI assertions.

Do not infer valid authentication from an installed extension, profile files, a setup marker, or a prior manual sign-in. Record runtime authentication as **not assessed by preflight**; this does not prevent preflight success. The setup guide requires manually established Copilot sign-in and records developer confirmation without account identifiers. M1-06 owns live sign-in detection; later positive sign-in-required/expired-auth observations must use an authentication-specific `BLOCKED` reason, distinct from missing extension. Unknown state is never labeled authenticated or missing-extension. This story neither reads Keychain/token storage nor adds a live authentication probe through Chat.

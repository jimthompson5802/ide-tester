## Objective and scope

Establish that the configured VS Code test profile is deliberately dedicated to testing and safely separated from personal resources. Preserve its existing contents and authentication. Integrate the qualified profile checks into the guarded run and provide a profile-safety setup guide.

The developer's latest scope instruction supersedes the earlier Q1–Q11 readiness requirements and broader acceptance mapping for M1-02. Only profile safety remains required:

- Validate the configured profile root, its `user-data` and `extensions` children, and their separation from protected or unrelated paths.
- Require a small nonsecret marker recording deliberate dedication to testing.
- Support deliberate manual adoption of the existing dedicated M1-00 profile after safety validation, preserving its contents and authentication.
- Inspect profiles read-only; report unsafe layouts and uncertain inspection distinctly.
- Demonstrate a successful profile-safety check and controlled unsafe-profile cases, with saved findings and no GUI operations.

A profile-safety pass establishes the checked paths and explicit dedication only. It does not prove arbitrary profile contents are safe or authorize profile deletion.

## Profile safety contract

The qualified layout matches the earlier spike:

```text
profile_root/
  .ide-smoke-profile.json
  user-data/
  extensions/
```

The qualified strict-JSON marker contains only `{"schema_version": 1, "purpose": "ide-smoke-dedicated-vscode"}`. Phase 1 confirmed its exact types, keys, bounded size, and file-kind rules in the guide. The marker records the developer's intent, not permission to delete or recreate the profile.

Reject home/filesystem roots, known everyday VS Code data/extension locations and their ancestors/descendants, symlink components, overlapping children, and installation or configured disposable-workspace overlap where applicable. Under the developer's 2026-10-21 decision, checkout overlap is allowed only for dedicated roots strictly beneath `<checkout>/profiles/`; the checkout itself, its ancestors, the `profiles` container itself, and other checkout locations remain rejected. Every other protection still applies. Exact qualified rules are in the [setup guide](../vscode-test-profile-setup.md). Use configured paths and filesystem metadata without qualifying or running an executable. Inspect the root, children, and marker with narrow allowlisted reads. Do not enumerate arbitrary profile contents, settings, extension manifests, account stores, or credentials.

Missing roots/children/marker, wrong kinds, malformed or unsupported markers, and positively unsafe layouts are `BLOCKED` with manual remediation. Permission-denied or indeterminate filesystem inspection is `HARNESS ERROR`; it must not be described as an absent or safe profile. A marker cannot override a rejected path. Preserve existing foundation diagnostic privacy and controlled reasons.

Adopting `profiles/m1-00` requires deliberate developer confirmation that it was created solely for testing, path/layout validation, and manual marker creation. Preserve the existing authenticated directory in place. Preflight never creates or repairs directories/markers, changes settings, copies profiles, signs in, or deletes profile data. Password/MFA automation and credential extraction remain prohibited.

## Technical approach and bounded decisions

Use two phases because the accepted spike leaves safety-critical lifecycle questions unresolved. Phase 1 qualifies the narrow launch/readiness/close mechanism using existing host tooling and synthetic fixtures. Phase 2 adds the production adapter and T01 only after the mechanism and its limitations are accepted. All new paths and symbols below are proposed until implemented.

The IDE adapter alone owns launch and cleanup. Shared code receives one IDE session, suitable for later injection into file and Copilot adapters. Keep the lifecycle interface platform-neutral and native imports in `src/ide_smoke/platforms/macos/vscode_session.py`, loaded only after supported-host selection. Do not create future editor/Copilot contracts or a plugin registry now.

Proposed minimal interface in `src/ide_smoke/adapters/base.py`: lifecycle operations for launch, readiness, close, and version retrieval, based on the proposal. Refine the launch/readiness signatures at P1-04 so both receive the same startup deadline; `launch(workspace)` followed by a fresh readiness timeout is insufficient. Use float seconds consistent with existing configuration. A proposed `VSCodeIDE` in `src/ide_smoke/adapters/vscode.py` coordinates these calls through the macOS session implementation. Keep native handles and process authority out of reports. Version retrieval must be bounded and tied to the selected application, without invoking a second arbitrary command or inspecting extension/authentication data.

Use one startup deadline measured with a monotonic clock from before launch through readiness, rather than granting a fresh full timeout after spawn. Bound native messaging, subprocess inspection, polling, and termination waits by explicit deadlines. Phase 1 must demonstrate control returns within the accepted bound even when a native call stalls; checking the clock only after that call returns is insufficient. A small isolated worker may be qualified if necessary, while preserving launch authority for cleanup/recovery. Adopt a fixed documented cleanup bound qualified in Phase 1; no new configuration key is assumed. Polling may observe progress but must not relaunch the IDE or retry T01.

Production policy to qualify in Phase 1:

1. Launch the configured, metadata-selected native VS Code application executable with the admitted profile's fixed `user-data` and `extensions` children and the current workspace. Construct an argument vector without a shell. Reject `code` wrappers and other unsupported launcher forms with a controlled explanation; wrapper handoff qualification is deferred. Do not silently substitute a different executable or installation. Discard Electron stdout/stderr by default.
2. Before spawn, positively detect an already-running use of the dedicated profile where the selected mechanism permits it. Refuse attachment or takeover; report a known conflict as `BLOCKED`. Uncertain ownership inspection is `HARNESS ERROR`. A regular VS Code instance using other paths is allowed. The guard serializes cooperating harness runs but does not prove a profile is otherwise unused.
3. Track launch authority immediately, including failures/interruption between spawn and first window. Qualify PID reuse defense using process birth/launch identity, selected executable, exact profile/workspace association, and before/after process identity. A window title substring, bundle ID, process name, or saved JSON alone cannot authorize cleanup. Do not copy the spike's command-string substring check into production.
4. Readiness requires a positively owned live application/window associated with this exact workspace and the agreed observable workbench structure, without an obstructing modal. This passive claim does not establish editor input or functional usability, which belong to M1-05. Phase 1 must choose the exact bounded AX predicate and demonstrate that a process alone, a welcome window, a wrong-workspace window, and ambiguous matching windows cannot pass. Temporary `AXManualAccessibility` on the positively identified owned application is permitted. Do not open/edit a fixture, type a command, submit a prompt, or automatically change persistent `editor.accessibilitySupport` to establish T01. Leave unexpected dialogs untouched, return a distinct controlled obstruction reason, and attempt owned cleanup. Record only an allowlisted obstruction category; an unrecognized dialog is a harness error, without inferred authentication or product causes. If passive workbench evidence is insufficient, stop to revise this approach before adding interactions or persistent settings changes.
5. Cleanup is registered before launch and must support never-started, partially started, ready, already-exited, and failed sessions. Revalidate identity before termination, including when no window ever appeared. Prefer the observed app-specific graceful shutdown. No global quit, process-name kill, broad process-group kill, stale-process adoption, or forced shutdown fallback is assumed. Ambiguous ownership, refusal, or shutdown deadline expiry produces a cleanup error and preserves resources for manual inspection. Confirm exit of the owned main application and positively associated processes that could still use the workspace. Phase 1 must qualify descendant tracking, including reparenting; shared or ambiguous processes never become termination targets. Uncertainty prevents workspace deletion and produces a cleanup error.
6. Preserve the authenticated profile: never delete, copy, reset, inspect credentials, or enumerate chat/account contents. Normal VS Code startup may update its own caches/state; do not claim byte-identical whole-profile preservation. Verify marker/layout and synthetic sentinels independently. Existing authentication is neither revalidated nor assumed renewed by T01.

Candidate controlled outcomes, finalized at P1-04: known missing execution/GUI/Accessibility prerequisites or occupied dedicated profile are `BLOCKED`; spawn/inspection errors, early exit without a proven product assertion, identity ambiguity, and unexplained readiness deadline expiry are `HARNESS ERROR` with distinct fixed reason codes. A product `FAIL` requires an observed assertion mismatch, not a guessed cause. Record elapsed T01 time for successes, failures, and interruptions, distinguishing startup/early-exit errors from readiness timeout. An interruption during T01 records that test as `HARNESS ERROR` with an interrupted reason and duration, skips T02–T05, and attempts cleanup; preserve the existing interruption exit policy and separate cleanup errors. Never echo native exceptions, process listings, raw window titles, settings contents, or environment dumps.

Within the agreed boundaries, evidence-dependent details remain assigned to the bounded Phase 1 checkpoint: exact native executable/ownership evidence, passive readiness predicate, bounded-call mechanism and deadline signatures, controlled obstruction categories, caller permissions prerequisites, cleanup/descendant tracking and completion, and minimal production dependencies. Phase 2 must be refined against the results before implementation. A choice requiring extra scope or new manual setup needs developer review; it is not implicit authorization.

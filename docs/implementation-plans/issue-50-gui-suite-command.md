- [tester instructions](../../smoke/AGENTS.md) and [usage](../../smoke/README.md) define dedicated profiles, real-only saved-authentication exceptions, Python preservation and recovery. Existing qualification records establish individual-suite history, not the new complete command.

## Technical approach

Use an uncompiled Node ESM entry point at proposed `smoke/scripts/test-gui.mjs`. It must run before any generated code is trusted, so a failed build cannot accidentally execute stale `dist/`. Use Node built-ins and argument arrays, no shell interpolation. Resolve the smoke package and checkout from the module URL, rather than the caller's directory. Run `npm run build` with the smoke directory as cwd; stream its existing diagnostics. Handle build spawn errors, signal termination and nonzero exit as a failed build stage with a harness-error command disposition, all three suites `not_run`, and nonzero exit. Always print a final summary on handled failure paths, including build failure.

After a successful build, dynamically import proposed compiled `dist/src/gui-command.js`. Use proposed `smoke/scripts/gui-arguments.mjs` as the single uncompiled syntax parser, with a narrow typed adapter in TypeScript. Validate syntax before building. Keep ordered suite orchestration and summary rendering in TypeScript modules. The bootstrap exposes a small injectable build/load/output boundary for non-GUI tests, with a guarded executable entry point. Test imports must never start builds or GUI work by themselves. Bootstrap build-failure presentation may be minimal, but must include the same required suite columns and a separate build reason; do not add a general orchestration framework.

Proposed `parseGUIArguments` adapts the shared uncompiled parser and accepts exactly one required `--build` and `--python-interpreter`, rejects duplicates, unknown flags, missing values, suite/backend overrides and invalid build syntax. Reuse existing single-suite validation where its meaning matches, without relaxing it. Preserve existing Python relative-path semantics: resolve the interpreter against the original invocation cwd before starting children in a fixed cwd, preserving the invocation symlink path rather than replacing it with its canonical target. After build, reuse `preparePythonInterpreter` for presence/resolution before any GUI launch; a known missing/non-file prerequisite is blocked with all suites `not_run`. Python retains its own preflight and runtime identity checks. Capture the original invocation directory using the agreed `INIT_CWD` policy before starting children. Do not preflight authentication or inspect profiles from the wrapper.

Proposed `runGUICommand` spawns the existing compiled CLI with `process.execPath`, explicit argv and `--output json`. Await each child and its complete output before deciding to launch the next. Routing is fixed:

| Entry | CLI arguments in addition to shared `--build <path> --output json` |
| --- | --- |
| basic | `--suite basic --chat-backend real` |
| git | `--suite git` |
| python | `--suite python --python-interpreter <absolute invocation path>` |

Use a focused injectable subprocess boundary for tests. Capture bounded stdout sufficient for existing reports, drain stderr without exposing raw real-backend diagnostics in the aggregate, and sanitize wrapper error messages. On stdout overflow, stop retaining excess bytes, keep draining both streams, request orderly cancellation once and await cleanup disposition; record the limit error separately from cancellation and cleanup. Validate JSON as `unknown`: allowed outcome, matching requested suite/backend when provided, finite nonnegative duration when provided, optional report path, and well-formed cleanup fields. Early blocked/harness results may lack ordinary metadata; preserve their classification and mark unavailable fields honestly. A malformed, oversized or contradictory response, child spawn/signal failure or unexpected exit status is a harness error. Do not reconstruct a lost result by scanning report directories or retrying a suite. Keep any available originating result and cleanup/reporting error distinct.

Advance only when child exit is zero, outcome is `passed`, there is no reporting error, cleanup errors are empty, `reservationRetained === false` and successful disposable cleanup is explicitly reported. Missing cleanup evidence fails closed as a harness error. Rely on the existing CLI shutdown contract and the next run's exclusive reservation acquisition; do not delete locks or add wrapper-owned reservations. A child that crashes or is interrupted does not establish GUI shutdown. Implement the cancellation lifecycle described below before relying on forwarded signals. Stop without starting another suite and direct deliberate existing recovery. Preserve existing individual lifecycle deadlines; do not add a wrapper timeout that releases resources or assumes a timed-out operation stopped.

Summary: one row per requested entry with suite, backend (`real` for basic; inapplicable for Git/Python), outcome (`passed`, `blocked`, `failed`, `harness_error`, `not_run`), duration and available individual report path. Use child total duration including cleanup; use measured elapsed duration for an attempted child lacking duration; use unavailable duration/report for unstarted entries. Include build status, total elapsed time, sanitized failure/recovery reason and cleanup/reporting errors where present. Individual JSON/text artifacts remain unchanged as suite evidence. The aggregate durably records observed subprocess/reporting failures, including emitted `reportingError` absent from saved individual JSON; such errors prevent batch success. Save aggregate `result.json` and `result.txt` under `reports/smoke-batches/<batch-id>/`; a new JSON CLI output option is unnecessary. Print brief progress without raw child JSON/stderr. Proposed `gui-bootstrap-report.mjs` owns the single persistence implementation: narrow canonical-path-checked aggregate directory creation, initial records and atomic per-file replacements. Proposed `gui-report.ts` calls it through a narrow typed adapter. Persist a running stage successfully before spawning each build or suite; failure prevents that launch. Update after build/preflight and each suite completion. Record batch ID, build/preflight state, total duration, ordered rows, incomplete/running/completed state, cancellation and separate cleanup/reporting errors. Report completion is independent of outcome: orderly cancellation can have a completed report; unfinished lifecycle or missing final evidence remains incomplete. Cancellation received before successful final aggregate commitment makes the command nonzero even if all suite rows passed; define and test that commitment cutoff. Atomic replacement is per file, not a cross-file transaction: a mismatch or incomplete record never establishes success. Establish storage before building when possible so build failures are recorded, and always before GUI; if storage is unavailable, print a terminal-only error/summary and return nonzero. Any later save failure stops subsequent launches. Treat partial reports as evidence, not permission to recover or delete reservations. Return zero only for three successful entries with confirmed cleanup and reporting; otherwise nonzero. An output/reporting contradiction must not become a pass.

#### Proposed cancellation boundary and ownership rules

Add a focused `cancellation.ts` boundary with a typed cancellation error, an idempotent request operation, observable requested state, a cancellation notification and a factory-based perform/check/settle contract. Keep signal installation separate from this run-local state. The first request stops scenario admission synchronously; further SIGINT/SIGTERM events only print sanitized shutdown-pending status. Imported `executeCLI`, `runSmoke`, `runFoundation` and workbench APIs install no global listeners. Existing callers use the default non-requested boundary; no new dependency is needed.

For each admitted operation, register the underlying promise before awaiting a cancellation/deadline race. Both fulfillment and rejection must be consumed, ownership-bearing results captured inside the raw operation, and the operation removed only after actual settlement. Check admission again after each await and inside polling callbacks before starting another action. The registry tracks composite scenario/turn promises as well as leaf operations. Shutdown may begin while admitted UI waits are pending so owned application close can unblock them; successful cleanup requires all such work to settle afterward. A rejected race is only a control-flow transition, never settlement evidence. This also applies to raw close, screenshot and trace promises: timing out their wrappers leaves cleanup uncertain until the underlying operation settles.

Keep cancellation-requested state separate from scenario-stopped state: scenario timeouts/errors also stop further scenario admission before cleanup, without inventing a user cancellation. Cleanup cannot reopen the scenario boundary. Use a narrow cleanup path for owned close, pending-work settlement, permitted existing evidence collection, preservation comparison and mock shutdown. Existing temporary Chat export removal remains owned cleanup; cancellation must not start a fresh export, prompt, save, commit or other scenario step. Real-mode screenshots/traces remain prohibited.

#### Lifecycle and deadline contract

| Stage at first cancellation | Stop/settlement behavior | Shutdown and release contract |
| --- | --- | --- |
| Before resource creation | Start no run, profile, mock or app operations; produce cancelled `harness_error` with unavailable run/cleanup fields. | No reservation was acquired. Do not claim cleanup of a run that never existed. |
| During resource/prelaunch preparation | Stop scheduling subsequent preparation. Retain and await already-started work within the cleanup deadline, capturing any late owned resource or mock handle. | Pending Electron launch | Stop first-window/readiness/scenario work. Rejection without a handle remains uncertain under the existing contract. Budget expiry retains reservation/resources; a later in-process handle remains owned and gets a bounded best-effort close without retroactively releasing anything. Process loss cannot guarantee later cleanup. |
| Readiness or active scenario | Stop new actions at every action factory/callback and acceptance boundary. Preserve completed checks and partial active evidence. Stop PythonDeadline and the common scenario boundary. Retain raw leaf, turn and scenario promises. | Begin owned app close without waiting indefinitely for UI waits; then require actual exit and settlement of all admitted work. | Diagnostics or cleanup already running | Permit only settlement, available evidence, preservation and owned shutdown operations. | Result persistence/presentation | Retain existing checks and cleanup evidence; apply cancelled command disposition before final report/output commitment and return nonzero. Start one absolute 120-second cleanup deadline when the runner first leaves scenario/preparation execution because of completion, error, expiry or cancellation, before optional diagnostics. Reuse that deadline if cancellation arrives during cleanup. This extends Python's existing shared-budget model to cancellation/settlement in all suites while retaining existing operation caps: ordinary close at most 10 seconds, actual-exit wait at most 5 seconds (using the shared owned-exit helper with an explicit remaining close/exit budget), screenshot/trace/mock close each at most 5 seconds; Python close at most 60 seconds within its existing 120-second budget. Every cap is reduced by remaining cleanup time. Launch remains capped at 60 seconds; ordinary UI operations at 15 seconds; existing suite and real-Chat turn deadlines remain unchanged. No wrapper deadline or process-wide kill is introduced.

Once admission is stopped, quiescence means every registered raw operation and scenario/turn continuation has settled and cannot start new scenario work. If the safety/settlement cleanup budget expires before final deletion is admitted, consume later promise results/rejections but retain the reservation and resources. Best-effort late-handle shutdown cannot turn that uncertain run into a pass or release its reservation. The accepted termination evidence remains the owned main process; detached/reparented descendants are outside existing guarantees.

`finishRun` must evaluate pass/removal eligibility at the point of removal, using current cancellation state rather than only the boolean captured on entry. A cancellation observed before removal starts retains unsuccessful resources. Already-started owned deletion may finish; preserve reports and report the actual disposition rather than promise rollback. Reservation release still requires ownership checks, confirmed main-process exit where launched, settled work, successful mock shutdown and applicable preservation comparison. Fail-closed uncertainty applies even if the process has exited.

Final filesystem commitment needs an explicit limitation: Node filesystem deletion is not cancellable. The 120-second budget bounds safety/settlement waits and admission of final removal, not a guarantee that an admitted filesystem call terminates by that deadline. Complete and settle ownership reads before deletion; immediately before resource deletion and reservation removal, verify the safety prerequisites and remaining budget again. Once a deletion is admitted, await its actual completion instead of racing it and claiming retention. If budget expires after resource deletion but before reservation removal, retain the reservation and report resources as actually removed. If reservation removal already began, report its actual completion/error; do not promise rollback or retention after that commitment. Stalled final filesystem I/O may therefore leave command finalization pending beyond the safety budget, with no successful result emitted. This limitation, including honest partial cleanup disposition, must be tested and approved at P1-Design-DV.

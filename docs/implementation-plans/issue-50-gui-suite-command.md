# Issue #50 — Run real basic, Git and Python with one npm command

Source: [GitHub issue #50](https://github.com/jimthompson5802/ide-tester/issues/50). Planning date: 2026-10-24.

Status: revised after developer-confirmed grill-me clarification; ready for developer review. The developer authorized this plan revision only; no implementation or GUI execution is authorized by this document. All paths and new symbols below are proposed unless identified as existing.

## Scope and current state

Deliver `npm --prefix smoke run test:gui -- --build "/Applications/Visual Studio Code.app" --python-interpreter "/absolute/path/to/python"`. Build once, then run `basic --chat-backend real`, standalone `git`, and standalone `python`, sequentially. Stop at the first unsuccessful stage, without retries. Summarize all three entries, including those not run.

Exclude additional suite selections, mock mode, foundation qualification, unrelated negative qualifications, parallel execution, automatic sign-in, profile resets, dependencies, retained-environment changes and unrelated runner refactoring. The developer explicitly added cancellation support and one interruption qualification during clarification; these supersede the original wrapper-only approach and interruption exclusion for this story.

Verified by source inspection:

- [package.json](../../smoke/package.json) has no `test:gui`; `build` runs lint, formatting checks and both TypeScript compilations. Tests execute compiled JavaScript with `node:test`.
- [cli.ts](../../smoke/src/cli.ts) exports `executeCLI` and prints a single JSON result with `--output json`, including early errors. It returns nonzero for unsuccessful execution or text-report writing errors. Some early harness errors have no report path.
- [arguments.ts](../../smoke/src/arguments.ts) rejects Python interpreter options outside Python and real backend selection for Git/Python. The wrapper must route arguments rather than forward the complete input list.
- [runner.ts](../../smoke/src/runner.ts) awaits owned application shutdown and `finishRun` before writing its JSON result. Cleanup errors change the final outcome to `harness_error`. Basic contains editing and Chat checks; it remains one wrapper entry.
- [resources.ts](../../smoke/src/resources.ts) exclusively acquires the shared reservation. Successful cleanup removes disposable resources and releases the reservation; failed scenarios can retain resources while releasing the reservation. Uncertain cleanup retains the reservation. Never infer safety merely from child-process exit.
- [report.ts](../../smoke/src/report.ts) distinguishes outcomes and separately reports cleanup. A text-report write failure can return nonzero with JSON `outcome: passed` and `reportingError`; the wrapper must check both.
- [tester instructions](../../smoke/AGENTS.md) and [usage](../../smoke/README.md) define dedicated profiles, real-only saved-authentication exceptions, Python preservation and recovery. Existing qualification records establish individual-suite history, not the new complete command.

Prerequisites for implementation: separate developer instruction and available existing Node/dependency tooling. GUI prerequisites: separate authorization covering the command and applicable preserved profiles, an unlocked exclusively reserved desktop, compatible installed VS Code, dedicated real-profile setup with permitted saved authentication, Git, Marketplace/network access as applicable, and the supplied interpreter. Missing prerequisites are blocked, never passed. There are no unresolved product choices requiring a feasibility phase; unexpected incompatibilities stop dependent work for plan refinement.

## Developer clarification — grill-me discussion

The `mattpocock-skills:grilling` (grill-me) skill helped clarify this plan through questions Q1–Q16. The developer answered yes to all decisions and explicitly confirmed the shared understanding and plan update. These are planning decisions, not implementation or GUI authorization:

1. Preserve separate Node CLI processes for each suite, with strict result/cleanup validation.
2. Validate argument syntax, build, then use the existing filesystem-only interpreter preflight before any GUI launch. Missing interpreter blocks all suites.
3. Add orderly cancellation to the existing CLI/runner in its own implementation phase. Stop new actions, settle pending operations and perform bounded owned cleanup. Forwarding SIGINT to the current CLI alone is insufficient.
4. Record cancellation as `harness_error` with an explicit cancelled-by-user reason, preserve active evidence, mark later suites `not_run`, and keep cleanup status separate. Repeated interrupts during cleanup do not bypass cleanup; print that shutdown is pending. SIGKILL/process loss remain outside orderly-cleanup guarantees.
5. Resolve relative interpreter paths against npm's original invocation directory (`INIT_CWD`), falling back to `process.cwd()` for direct Node execution; preserve invocation symlink spelling.
6. Save aggregate JSON/text in `reports/smoke-batches/<batch-id>/`, without another desktop reservation. Establish writable storage before GUI execution, write an initial record and atomically update after completed stages. Interrupted records remain explicitly incomplete; a stale running entry never establishes shutdown or success.
7. Aggregate initialization failure prevents GUI execution. Later reporting failure prevents subsequent suites and returns nonzero while retaining individual evidence and printing available results.
8. Print brief suite-start/completion progress, elapsed time, outcome and report path; suppress raw child JSON/stderr in aggregate terminal output.
9. Require a separately authorized interruption run, then a fresh uninterrupted complete-command pass. Require the complete pass to use a space-containing interpreter invocation path through an owned disposable directory alias preserving installation structure. Create it before preservation capture; remove it only after confirmed shutdown. Refine a rejected fixture rather than weaken protection.
10. Use three phases: cancellation/non-GUI verification; aggregate command/tests/documentation; separately authorized GUI qualification. Each ends at an explicit developer validation gate.

Source inspection during clarification found no existing SIGINT/SIGTERM cancellation handlers in `smoke/src/cli.ts`, `smoke/src/runner.ts` or `smoke/src/resources.ts`. Existing `preparePythonInterpreter(supplied, cwd)` in [python-interpreter.ts](../../smoke/src/python-interpreter.ts) returns supplied, absolute and canonical paths using only filesystem checks. npm changes the script cwd to the package directory and supplies `INIT_CWD`; the bootstrap must explicitly preserve that original-directory policy. `createRun` cannot be reused for aggregate storage because it acquires the child suites' reservation and creates GUI resources. These findings motivate the revised boundaries below.

## Technical approach

Use an uncompiled Node ESM entry point at proposed `smoke/scripts/test-gui.mjs`. It must run before any generated code is trusted, so a failed build cannot accidentally execute stale `dist/`. Use Node built-ins and argument arrays, no shell interpolation. Resolve the smoke package and checkout from the module URL, rather than the caller's directory. Run `npm run build` with the smoke directory as cwd; stream its existing diagnostics. Handle build spawn errors, signal termination and nonzero exit as a failed build stage with a harness-error command disposition, all three suites `not_run`, and nonzero exit. Always print a final summary on handled failure paths, including build failure.

After a successful build, dynamically import proposed compiled `dist/src/gui-command.js`. Keep argument parsing, ordered suite orchestration and summary rendering in corresponding TypeScript modules. The bootstrap exposes a small injectable build/load/output boundary for non-GUI tests, with a guarded executable entry point. Test imports must never start builds or GUI work by themselves. Bootstrap build-failure presentation may be minimal, but must include the same required suite columns and a separate build reason; do not add a general orchestration framework.

Proposed `parseGUIArguments` accepts exactly one required `--build` and `--python-interpreter`, rejects duplicates, unknown flags, missing values, suite/backend overrides and invalid build syntax. Reuse existing single-suite validation where its meaning matches, without relaxing it. Preserve existing Python relative-path semantics: resolve the interpreter against the original invocation cwd before starting children in a fixed cwd, preserving the invocation symlink path rather than replacing it with its canonical target. After build, reuse `preparePythonInterpreter` for presence/resolution before any GUI launch; a known missing/non-file prerequisite is blocked with all suites `not_run`. Python retains its own preflight and runtime identity checks. Capture the original invocation directory using the agreed `INIT_CWD` policy before starting children. Do not preflight authentication or inspect profiles from the wrapper.

Proposed `runGUICommand` spawns the existing compiled CLI with `process.execPath`, explicit argv and `--output json`. Await each child and its complete output before deciding to launch the next. Routing is fixed:

| Entry | CLI arguments in addition to shared `--build <path> --output json` |
| --- | --- |
| basic | `--suite basic --chat-backend real` |
| git | `--suite git` |
| python | `--suite python --python-interpreter <absolute invocation path>` |

Use a focused injectable subprocess boundary for tests. Capture bounded stdout sufficient for existing reports, drain stderr without exposing raw real-backend diagnostics in the aggregate, and sanitize wrapper error messages. Validate JSON as `unknown`: allowed outcome, matching requested suite/backend when provided, finite nonnegative duration when provided, optional report path, and well-formed cleanup fields. Early blocked/harness results may lack ordinary metadata; preserve their classification and mark unavailable fields honestly. A malformed, oversized or contradictory response, child spawn/signal failure or unexpected exit status is a harness error. Do not reconstruct a lost result by scanning report directories or retrying a suite. Keep any available originating result and cleanup/reporting error distinct.

Advance only when child exit is zero, outcome is `passed`, there is no reporting error, cleanup errors are empty, `reservationRetained === false` and successful disposable cleanup is explicitly reported. Missing cleanup evidence fails closed as a harness error. Rely on the existing CLI shutdown contract and the next run's exclusive reservation acquisition; do not delete locks or add wrapper-owned reservations. A child that crashes or is interrupted does not establish GUI shutdown. Implement the cancellation lifecycle described below before relying on forwarded signals. Stop without starting another suite and direct deliberate existing recovery. Preserve existing individual lifecycle deadlines; do not add a wrapper timeout that releases resources or assumes a timed-out operation stopped.

Summary: one row per requested entry with suite, backend (`real` for basic; inapplicable for Git/Python), outcome (`passed`, `blocked`, `failed`, `harness_error`, `not_run`), duration and available individual report path. Use child total duration including cleanup; use measured elapsed duration for an attempted child lacking duration; use unavailable duration/report for unstarted entries. Include build status, total elapsed time, sanitized failure/recovery reason and cleanup/reporting errors where present. Individual JSON/text artifacts remain authoritative and unchanged. Save aggregate `result.json` and `result.txt` under `reports/smoke-batches/<batch-id>/`; a new JSON CLI output option is unnecessary. Print brief progress without raw child JSON/stderr. Proposed `gui-report.ts` owns narrow canonical-path-checked aggregate directory creation, initial records, and atomic per-file replacements after build/preflight and each suite completion. Record batch ID, build/preflight state, total duration, ordered rows, incomplete/running/completed state, cancellation and separate cleanup/reporting errors. Atomic replacement is per file, not a cross-file transaction: a mismatch or incomplete record never establishes success. Establish storage before building when possible so build failures are recorded, and always before GUI; if storage is unavailable, print a terminal-only error/summary and return nonzero. Any later save failure stops subsequent launches. Treat partial reports as evidence, not permission to recover or delete reservations. Return zero only for three successful entries with confirmed cleanup and reporting; otherwise nonzero. An output/reporting contradiction must not become a pass.

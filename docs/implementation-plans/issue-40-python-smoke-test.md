## Proposed contracts and technical approach

All new paths, names, flags, schemas, and deadlines below are design targets until implemented. Phase 1 must refine UI-dependent details before phase 2 starts.

### Invocation and interpreter identity

Proposed invocation, from the repository root after compilation and authorization:

```sh
npm --prefix smoke run smoke -- \
  --build "/Applications/Visual Studio Code.app" \
  --suite python \
  --python-interpreter "/Users/jim/Desktop/genai/ide-tester/.venv/bin/python"
```

`--python-interpreter` is required for Python, rejected for other suites, and accepts an executable file path rather than a command with arguments or a PATH lookup. Resolve relative paths against the invocation working directory before any workspace/child-process change. Missing values, duplicates, invalid combinations, nonexistent files, directories, non-executable files, and unusable interpreters must produce clear nonzero blocked results. `qualify --suite python` is unsupported. Real Chat is unsupported for Python; the default `mock` option does not start a mock server or select Chat.

Proposed `preparePythonInterpreter` in `smoke/src/python-interpreter.ts` keeps three distinct values: original input, absolute invocation path, and canonical executable path. Probe the **absolute invocation path**, not its realpath, using a bounded `execFile` argument array and a standard-library-only `-I -B -c` identity probe. Capture validated JSON containing `sys.executable`, version, `sys.prefix`, and `sys.base_prefix`; require exit zero and a canonical executable matching the supplied path. Never execute `hello.py` from the harness. Preflight output cannot count as IDE execution evidence.

Preserving the invocation path matters for virtual environments whose executable symlinks resolve to a shared base Python. Pass that absolute path through the interpreter picker. Canonical `sys.executable` equality satisfies the issue's symlink comparison; also compare the IDE execution's normalized prefix/base-prefix with the probe to reject a different environment using the same underlying binary. Do not require every interpreter to be a virtual environment, or hard-code Python 3.12.15 as a universal supported version. Record the actual version and qualify only combinations exercised.

### Isolation and installation

Proposed `pythonProfile` in `smoke/src/python-profile.ts` owns ignored `profiles/smoke-python/{user-data,extensions,state}` with marker `ide-tester:smoke-python:v1`. Create only an absent profile; reuse only an explicitly owned, non-redirected, closed profile. Reject unowned directories, symlinked/redirected state, malformed settings, and stale/active singleton locks without deleting or adopting them. Preserve this profile on every outcome. Do not use Git or real Chat profiles, copy authentication, or modify profile databases to select interpreters or enable extensions.

Use existing common editor/startup isolation settings, disable Chat/Copilot for this instance, use `--use-inmemory-secretstorage`, and avoid mock endpoints, synthetic tokens, proxies, Git preparation and the Chat helper. Launch with an allowlisted environment and owned disposable home/tmp directories; exclude inherited Python environment/path overrides such as `PYTHONHOME`, `PYTHONPATH`, and `VIRTUAL_ENV`. Use a shell configuration that does not read personal startup files. Determine the precise terminal/Python settings in phase 1, including preventing environment creation/package bootstrap; persist only a documented small set of owned settings and preserve unrelated keys/state. Normal interpreter selection must remain a UI action.

Scope Extensions UI observations to exact ID `ms-python.python` and Microsoft publisher identity. If absent, click Install and wait for installed **and enabled** state; if present, record reuse, inspect enabled state and enable through UI if necessary. Record before/after state, action taken, exact version, and discovered required extension dependencies. Do not update/uninstall a reused extension merely to simulate installation. A reused-profile pass verifies reuse; fresh-install acceptance additionally needs an authorized initially absent-profile run. If an extension requires reload, either implement an observed bounded owned-window reload path after phase-1 validation or stop and refine the plan; do not silently skip readiness checks.

### Saved program and independent evidence

Proposed `smoke/src/python-evidence.ts` generates the standard-library-only source and validates execution evidence. Proposed `checkPython` in `smoke/src/python.ts` orchestrates the scenario through focused workbench operations, without embedding selectors or writing `hello.py` directly.

The program must:

1. Print the exact line `Hello, world!` and a separate structured identity line containing the unique current run ID, `sys.executable`, version, prefix and base-prefix.
2. Derive output paths from its own `__file__`, with evidence names unique to the run, inside the disposable workspace. Include the run ID, canonicalizable script path and interpreter identity in a versioned JSON payload.
3. Flush output, write evidence using an exclusive temporary file and atomic replacement into an initially absent completion destination, and print a unique completion line. Exceptions must remain errors; no success record after an earlier failure.

Before dispatch, require absence of the script and all evidence destinations, create/save the source exclusively through editor UI, compare exact saved UTF-8 bytes and SHA-256 independently, reopen and inspect it, and verify bytes again. Encode run IDs/paths as data when generating source, never by interpolating unescaped shell text. The harness reads evidence; only the IDE-run program writes it.

Select the absolute invocation path through **Python: Select Interpreter**, using the explicit-path flow even when discovery lists another Python. Verify the selection UI/status, keep `hello.py` active, establish a fresh owned terminal/baseline with no run markers, then invoke the extension's **Run Python File in Terminal** action exactly once. Command labels/IDs, picker flow and terminal targeting require installed-app verification in phase 1.

Passing requires all of: freshly observed greeting and identity/completion lines for this run in the targeted terminal after dispatch; exact independently verified saved source; a regular non-symlink completion file inside the owned workspace with a valid complete schema, current run ID, correct script path and matching interpreter/environment; and observed successful completion of this specific terminal command. Prefer shell-integration exit status zero if available. Phase 1 must prove a reliable completion/exit observation; a greeting, JSON file, command echo, fixed delay, or completion token alone cannot prove successful execution. If the installed app cannot expose sufficient evidence, stop for developer review before implementation rather than weaken the criterion.

Use the never-before-used workspace/run ID, pre-dispatch absence, targeted terminal baseline, program output and completion observation together for freshness. Do not rely solely on timestamps, which can be coarse or manipulated. Reject stale IDs, wrong script/interpreter/environment, malformed or partial JSON, escaped/symlinked destinations, missing output, nonzero exit, interrupted runs and timeouts. Continue to verify the saved source has not changed before accepting results. Bound file size and observation polling; do not read unrelated terminal history or user files.

### Reporting and failure handling

Extend check evidence with stage, installation mode (`fresh`/`reused`), enabled/installed observations, Python/dependency versions, supplied/absolute/canonical interpreter paths, probe identity, saved-file digest, selected-interpreter UI observation, targeted terminal output/completion/exit evidence, parsed program evidence, and timings. Preserve available partial evidence on every outcome, along with existing resource/profile paths and cleanup results. Record observed values rather than substituting expected values. Text output should show the Python stage, install/reuse mode and interpreter/version, with JSON holding full bounded evidence.

| Outcome | Examples |
| --- | --- |
| `blocked` | Missing/unusable interpreter; unsupported host/app checkpoint; profile already open; positively identified Marketplace connectivity/policy prerequisite; unavailable manual authentication. |
| `failed` | Installation/enablement fails despite satisfied prerequisites; valid UI selection yields the wrong runtime; saved bytes differ; stale/mismatched execution evidence; program error/nonzero exit; execution fails to finish within its deadline. |
| `harness_error` | Unknown/changed UI contract; missing terminal observation capability; malformed ownership/settings; internal filesystem/reporting error; uncertain application/terminal shutdown. |

Do not call every install timeout a connectivity block: retain stage and known observations, and distinguish an identified prerequisite from a functional timeout or broken observation contract. Proposed limits: interpreter probe 10 seconds, existing launch limit 60 seconds, extension readiness 180 seconds, interpreter selection 60 seconds, execution 60 seconds, and an overall Python limit sufficient to contain these stages (initial target 360 seconds). Use observable waits and one sequential run with zero automatic retries. Phase 1 must confirm/refine limits and completion cancellation. A timeout does not prove the operation stopped: stop/close only the owned app and terminal process tree, verify shutdown before releasing resources, and retain resources/reservation when shutdown is uncertain. Preserve suite outcome separately if cleanup changes the final disposition to `harness_error`.

# Issue #38: VS Code Git smoke test

Source: [GitHub issue #38](https://github.com/jimthompson5802/ide-tester/issues/38). Planning date: 2026-10-23.

Status: technical plan revised to reflect developer-confirmed shared understanding on 2026-10-23. No implementation or GUI qualification has been performed for this story. All new paths and symbols below remain design targets; phase validation gates remain unchecked.

## Shared understanding from the grill-me review

The following decisions were derived using the grill-me discussion with the `mattpocock-skills:grilling` skill and explicitly confirmed by the developer. This records design agreement, not implementation authorization or completed phase validation.

1. **Required Graph evidence:** a pass requires the expected commit to appear in VS Code's Source Control Graph as well as independent Git verification. A successful commit without the required Graph observation does not pass.
2. **Controlled Git configuration:** use isolated Git configuration, a repository-local synthetic author, disabled commit signing and disabled hooks. Personal signing configuration and custom hooks are outside this story's coverage; global Git configuration remains unchanged.
3. **Combined order and failure behavior:** `all` runs editing → Git → Chat. Preserve fail-fast behavior: a Git failure stops the combined run and leaves Chat `not_run`. Standalone Chat remains available for independent checks.
4. **Real combined acceptance:** passing `all --chat-backend real` is mandatory before accepting this story, alongside mocked combined validation. Missing authentication or service prerequisites leave acceptance pending; they do not waive this check.
5. **Harness-managed dedicated profile:** preserve `profiles/smoke-git` between runs, while allowing the tester to maintain explicitly owned test settings and relevant saved UI state. Allowed maintenance includes mock endpoint refresh for mocked combined runs, autosave/simple-dialog test settings, and Source Control Graph filter/repository-selection reset. Personal VS Code profiles, settings, extensions and saved UI state remain untouched. Exact managed keys and reset operations must be documented in phase 1; this is not unrestricted profile mutation.
6. **No mock server for Git-only:** `--suite git` launches VS Code and tests Git without starting the mock Chat server. Mocked `all` starts the server because it selects Chat; real `all` uses real Copilot without a mock server.
7. **Commit matching:** the exact unique commit message visible in Graph is sufficient UI evidence when independent Git checks establish that the fresh repository contains exactly one commit with that message and the expected file contents. Record the full hash from Git; displaying or revealing the hash in the UI is not required.

## Scope and acceptance

Implement a local Git journey in the standalone TypeScript tester: initialize the owned workspace through VS Code, create/save one known file in the editor, stage and commit it through Source Control, display the commit in Source Control Graph, and independently confirm the commit with Git commands. Add `--suite git`; extend `all` to editing → Git → Chat. Keep standalone editing and Chat behavior intact.

Issue acceptance criteria, numbered in source order for traceability:

1. Git suite selection and outcome reporting through the existing CLI.
2. UI initialization of a disposable workspace that initially has no repository.
3. Editor creation and save of a known file.
4. Visible Source Control file, UI staging, known message, and UI commit.
5. Visible expected commit in Source Control Graph.
6. Independent commit hash/message/content checks and confirming `git log` evidence in the report.
7. Repository-local synthetic author; unchanged global Git configuration; no remote/authentication requirement.
8. Blocked prerequisites distinguished from functional failures and harness errors; non-GUI success is not GUI qualification.
9. Editing/Chat regression coverage and accurate Git usage/verification documentation.
10. Existing repositories, profiles, retained workspace data, and settings preserved; cleanup limited to owned resources.

Exclusions: clone, remotes, push/pull, branches as test scenarios, merge conflicts, GitHub sign-in, generated commit messages, Python changes, new platform/version support, and advancement of unrelated real-Chat validation gates. No neighboring-checkout build or runtime dependency and no new package dependency is planned.

## Technical approach

Separate UI actions from independent repository evidence. Proposed `smoke/src/git.ts` exports `checkGit(...)`, coordinates the journey, and holds partial evidence. Proposed `smoke/src/git-repository.ts` owns bounded Git subprocesses, repository identity checks, local author configuration, and evidence verification. Keep UI interactions on `Workbench` in `smoke/src/workbench.ts`; do not add Git actions to the helper extension.

Use `execFile` with argument arrays, explicit working directory, restricted environment, bounded output, timeout and process termination. Do not use a shell. Probe Git availability before GUI launch; prevent a missing macOS command-line-tools installation from triggering an unattended installation dialog. Clear inherited `GIT_DIR`, `GIT_WORK_TREE`, index/config/author overrides and other unintended Git routing variables by constructing the child environment. Git configuration isolation must also apply to the launched VS Code Git extension, not only verifier subprocesses. Use an owned empty global configuration and disable system configuration for the Git journey; verify the pinned extension honors this in phase 1. No read or write of the developer's personal Git configuration is needed.

Before initialization, require an owned canonical workspace, absent `.git`, and no enclosing repository. After UI initialization, require `.git` to be a real directory inside that exact workspace and Git's top-level path to equal it. Reject symlinks or redirected worktrees. Only then write local test identity and local deterministic commit settings, including disabled signing and an owned empty hooks directory to disable hooks. Never initialize, stage, or commit through subprocesses in the production journey. Repository-local configuration and read-only verification are the permitted subprocess operations.

Use a unique synthetic commit message, fixed filename, and known UTF-8 content. Stage only `git-smoke.txt`, leaving existing editing fixtures untracked. Require an initially unborn HEAD and empty index; after committing, require one root commit, exactly the expected tracked path and bytes, and the synthetic author. Do not assert a globally clean worktree because `existing.txt` and possibly `created.txt` remain untracked. Verify there are no staged leftovers instead.

Collect a bounded `git log -1` result with hash and subject, verify HEAD consistency, and inspect the committed blob directly rather than only the working file. Require both the visible Graph message and independent repository evidence. Match the Graph row by the exact unique test message and independently require exactly one root commit with that message and the expected committed file. Record the full hash from Git; no extra UI interaction to expose the hash is required. Do not substitute terminal `git log` output for visible Source Control Graph acceptance.

Proposed evidence includes current stage, initialization confirmation, filename, expected/observed message, full commit hash, test author, content digest/byte count, tracked paths, Graph observation, bounded log output, Git version and per-stage completion. Preserve available partial evidence on failure and timeout. JSON holds structured evidence; text reports should show a concise confirming hash/message/log line as well as the Git outcome. Never include whole configurations, arbitrary logs, account details, or unrelated desktop content.

Classify unavailable Git/tool prerequisites as `blocked`; known UI actions that complete with wrong contents/history or time out waiting for their functional result as `failed`; unavailable selector/command contracts, malformed evidence, unsafe ownership, subprocess infrastructure faults and cleanup uncertainty as `harness_error`. Identify the stage and sanitized cause. Separate contract absence from an unsuccessful product operation where evidence allows; do not classify every selector timeout as a product defect. A proposed `GitFailure` carries outcome and partial evidence without importing Git concepts into Chat logic.

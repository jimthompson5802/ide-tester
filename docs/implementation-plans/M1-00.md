### Required validation cases

- **Freshness and prompt echo:** A prompt visibly contains `READY`, and history may already contain an assistant response equal to `READY`. Neither can pass before a new assistant turn associated with the current submission completes. Perform a real stale-history rejection check in the owned VS Code instance with prior synthetic assistant text, and verify echoed input cannot satisfy the response check. Capture the prior conversation/turn boundary and observe the new assistant role/turn and corresponding lifecycle; use observed IDs, ordering or equivalent correlation. If IDs do not persist across restarts, establish a new baseline each launch. A global search for `READY` is insufficient. Synthetic state tests supplement this required host evidence.
- **Completion:** Record the response-associated UI state transition that signifies completed generation, plus checks for exposed error/cancellation states. Idle input or disappearance of a stop control alone may also follow cancellation/error; validate how the method distinguishes those outcomes. Unchanged text, a quiet interval, or a fixed sleep alone never establishes completion. A fast response need not expose every streaming frame, but it must still have a verified terminal signal associated with the new assistant turn.
- **Unsuccessful/ambiguous generation:** Demonstrate an actual controlled cancellation in VS Code using only a harmless synthetic prompt within the test conversation, and verify the cancelled response cannot pass as completed. This is mandatory; if it cannot be demonstrated, report the missing evidence and return for a developer decision before a go recommendation. Inspect error-state exposure when safely available; avoid changing host networking or credentials to manufacture failures. Error states that cannot safely be reproduced remain explicitly unverified. Add non-GUI cases for stalled partial text, error, cancelled, unknown and timeout observations, proving they cannot pass. Mark simulated states versus on-host observations explicitly. If completion remains indistinguishable from error or cancellation, stop for a design decision before feasibility approval.
- **Authentication:** Investigate the sign-in-required state before initial manual sign-in where possible. If unavailable, a separate disposable unauthenticated test profile may be used without copying credentials or signing out the authenticated profile; record whether the state was actually observable. An explicit authentication-required state is `BLOCKED`; a missing extension is a different prerequisite; unknown UI is not proof of expired authentication. Successful requests after a full restart provide reuse evidence; an installed extension or visible Chat panel alone does not.
- **Independent decision logic:** Where the scripts introduce state/assertion logic, use focused standard-library tests for rejection of stale/echoed/partial/cancelled/error/unknown responses, timeout, and exact matching after whitespace trimming. `READY\n` passes after verified completion; `Ready!`, Markdown-wrapped `READY`, and extra words fail. No pytest dependency or new general test framework is needed for the spike. These checks must be created during implementation; no runtime tests exist now.
- **Ownership and cleanup:** Every action rechecks the intended test session/window as needed. Refuse to act on an uncertain target. Attempt bounded owned-instance cleanup after failures; record cleanup failure separately and preserve individual observations. Delete only validated disposable workspaces when appropriate; preserve the authenticated profile and useful failure evidence. Never close unrelated VS Code processes/windows.

At least two launches must show automated fresh, completed interaction and pass the exact `READY` assertion; record content-assertion outcomes separately from automation capability. Do not recommend go or silently relax the assertion after a mismatch: present the evidence for a developer decision. Retain both launches if configuration changes, record the differences and assess their impact at the final checkpoint without forcing a rerun solely for that change. Do not claim repeatability for a configuration tested only once. Additional launches may resolve a specific uncertainty within the time box; five consecutive unattended passing runs on unchanged versions/configuration belong to M1-09.

**Completion criteria:** T7–T10 provide the evidence or explicitly explain which capabilities could not be demonstrated. A completed report may recommend no-go; that is not a successful feasibility demonstration. A go recommendation requires demonstrated isolation/targeting with regular-window coexistence, compliant dependencies with reusable exact-version requirements, automated Chat with exact `READY` matches across two launches, live stale-history rejection, live cancellation rejection, fresh assistant-turn detection, response-associated completion distinguishable from error/cancellation, and restart authentication reuse. Safely unreproduced error states remain explicitly unverified; this cannot excuse a completion method that confuses error with success. `Go with limitations` may narrow language, model, channel or desktop conditions only with evidence and developer approval; it cannot waive core guarantees or the confirmed evidence requirements. Assess any configuration differences at the final checkpoint using the retained launch evidence, without automatic pair invalidation or claims of unproven repeatability.

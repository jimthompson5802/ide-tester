### CLI and configuration contract

Support `ide-smoke --help` and `ide-smoke run --ide vscode`, with an explicit `--config PATH` option. Resolve the default `config/harness.local.yaml` from the caller's current working directory, without automatic checkout discovery. A missing configuration file is a configuration usage error and must explain how to copy and edit the committed sanitized example. An explicit relative `--config` path also follows the caller's working directory. Resolve paths inside YAML relative to that configuration file, expand `~` consistently, and report the offending key and corrective action without dumping the document. Selecting a configuration elsewhere does not move the reports root.

Implement a deliberately smaller schema than the proposal's illustrative YAML:

| Proposed field | Validation / responsibility |
| --- | --- |
| `harness.platform` | Required `macos` for this milestone; unsupported platform fails explicitly. |
| `harness.execution_mode` | Required `sequential`; reject parallel operation. |
| `harness.timeouts.ide_startup_seconds` | Required positive finite numeric seconds; reject booleans, zero, negatives, infinity, and NaN. |
| `harness.timeouts.copilot_response_seconds` | Same validation; reserved for the later Copilot action, not exercised here. |
| `ides.vscode.executable` | Required nonempty path or CLI name; resolve names through PATH and check basic availability after parsing. An absent executable is `BLOCKED`, not invalid configuration. Do not describe an existing but nonexecutable file as missing; runtime runnability and IDE readiness remain M1-02. |
| `ides.vscode.profile_root` | Required explicit dedicated-profile directory. Validate the path value, then check availability; an absent profile is `BLOCKED`. Profile identity, extension readiness, and authentication remain M1-02. |

Reject unknown keys at every supported level, incorrect types, malformed/empty YAML, duplicate keys, missing required fields, and unreadable configuration as configuration usage errors. Use safe loading; never construct arbitrary Python objects from YAML. Future-only fields such as scheduling and IntelliJ must produce an actionable unsupported-key error. Document that the large proposal example is not an accepted configuration file. No configuration load creates a profile or disposable workspace.

Keep malformed settings distinct from unavailable resources: an otherwise valid configuration whose executable or profile is positively identified as absent produces run-level `BLOCKED`, exit 3, and all T01–T05 `SKIP` with that origin. Stop before the unimplemented-operation result so it cannot replace the identified block. If resource availability cannot be determined reliably, preserve the uncertainty as `HARNESS ERROR` rather than asserting absence. Availability checks do not launch VS Code, inspect profile contents, or drive the desktop.

Keep run evidence under `reports/<run-id>/`, resolved from the caller's working directory independently of configuration location. Reports are ignored when created in this checkout; another working directory does not inherit this repository's ignore rules. Do not add an output-location option for this story or make the desktop lock location configurable through YAML or a command-line switch. No screenshot or raw conversation capture is needed.

### Results, summaries, and failure handling

Use the exact public outcomes `PASS`, `FAIL`, `BLOCKED`, `HARNESS ERROR`, and `SKIP`:

- `PASS`: an executed test's observable assertion succeeded.
- `FAIL`: an observed product assertion failed, including a content mismatch.
- `BLOCKED`: a positively identified missing prerequisite prevents execution.
- `HARNESS ERROR`: execution or assessment is unreliable, an unexpected exception occurs, or required cleanup fails.
- `SKIP`: a dependent test did not execute; retain the originating result and reason.

Keep configuration/guard/run-level errors separate from T01–T05 results. Unimplemented execution is a run-level `HARNESS ERROR` with a specific unsupported-operation reason; T01–T05 remain `SKIP` with that origin. A foundation-only `run` cannot return success or imply the GUI tests ran. Later stories replace these unavailable operations as authorized. Tests may inject synthetic outcomes through an internal callable boundary; do not add public CLI flags that simulate passing IDE tests.

Use a fixed ordered list of T01–T05 with simple dependency stopping, not a general workflow engine. Preserve the first originating outcome, skip its dependent actions, and attempt registered cleanup in a `finally` path. In this story cleanup covers only acquired foundation resources and test doubles. Actual IDE process cleanup remains owned by the later IDE adapter. Cleanup failure is a separate `HARNESS ERROR`, preserves individual results, and makes the run nonzero.

Create a run ID and timestamped structured events for each admitted `run` invocation; include event name, result/reason where applicable, and sanitized messages. Save a minimal JSON summary containing run ID, start/end timestamps, selected IDE, run outcome/reason, all T01–T05 statuses and reasons, available durations, cleanup result, and exit code. Mark unavailable information explicitly; never invent version or timing observations. Bound individual future operations through timeout parameters; unit tests inject timeout exceptions rather than introducing a speculative thread/process timeout framework.

Use an explicit set of permitted diagnostic fields: the run/test/event metadata above, relevant configuration key or resource path, controlled reason codes/messages, and safe error identifiers needed to explain corrective action. Exclude configuration-document contents, credentials, environment dumps, prompts, responses, and unrestricted exception text or tracebacks. Apply the same content restrictions to saved reports, event files, and terminal output. Unexpected exceptions must map to controlled explanations without serializing their arbitrary contents.

Normal terminal output is brief: the result, an actionable explanation, and the saved report location. Store detailed structured events in report files. If no report was saved, say so instead of printing a success claim or implying that artifacts exist.

Finalize evidence for invalid configuration, blocked prerequisites, unexpected exceptions, timeouts, and lock rejection as far as the output filesystem permits. Establish the working-directory-relative reports root before loading YAML so malformed settings do not prevent basic diagnostics. If logging or summary creation itself fails, report the specific failure through controlled stderr diagnostics and return nonzero; do not claim an artifact was saved. Retain already available outcomes when finalization fails.

On a handled Ctrl-C, attempt cleanup, release owned resources, and finalize the report. Preserve completed test outcomes and mark remaining tests `SKIP` with the interruption origin; record a run-level `HARNESS ERROR` with an explicit interrupted reason, without adding a sixth public outcome. Exit 130 when interruption ends the attempt, unless cleanup or evidence finalization fails, in which case exit 4 and retain both reasons. No evidence or cleanup guarantee applies to a hard kill or machine failure.

Proposed documented exit-code mapping:

| Code | Meaning |
| --- | --- |
| `0` | All required T01–T05 assertions passed and cleanup succeeded; also ordinary help output. |
| `1` | At least one functional `FAIL`, without a harness error. |
| `2` | CLI/configuration usage error; a parsed `run` with invalid config records a configuration `HARNESS ERROR` reason when evidence can be saved. |
| `3` | Identified prerequisite `BLOCKED`, including a competing active run, without a higher-priority error. |
| `4` | Runtime `HARNESS ERROR`, unsupported implementation, cleanup failure, or evidence-writing failure. |
| `130` | Handled interruption, unless cleanup or evidence finalization fails and requires code 4. |

For admitted runs, aggregate runtime severity as `HARNESS ERROR` before `FAIL` before `BLOCKED`; `SKIP` never erases its cause. The handled-interruption exit-code rule above is explicit and preserves any earlier test outcomes. All-skipped or partially unimplemented suites cannot yield code 0. Usage errors occur before test execution; bare argument-parser errors need not create a run directory.

### Desktop-run exclusion

Qualify a standard-library OS advisory lock held on an open descriptor for the entire run, including cleanup. Isolate platform imports under a proposed `src/ide_smoke/platforms/macos/run_lock.py`; shared orchestration accepts the small acquire/release boundary. Unsupported platforms fail clearly without importing macOS-specific code.

Use one canonical per-macOS-user lock, proposed at `~/.ide-smoke/desktop-run.lock`, independent of checkout, IDE profile, workspace, output path, and config. The developer confirmed that every `run` invocation must contend on this lock, including foundation attempts that cannot yet drive the GUI. Conservatively serialize all runs for that user on this host; this covers the same-desktop-session requirement without requiring a new session-discovery mechanism. Help must remain usable while a run holds the lock.

Acquire nonblocking at admitted run entry, before configuration-dependent execution or any future preflight probe that drives the UI, IDE launch, or GUI action. A contender reports the active-run conflict, returns code 3, and writes only its own evidence. It must not truncate active metadata, release another process's lock, delete the lock file, signal the owner, or invoke owner cleanup. Lock-file existence/PID metadata alone is not proof of an active lock. Never unlink the shared file during ordinary release: changing its inode can defeat exclusion. Qualify normal release and process-exit behavior; automatic lock release after a crash does not establish cleanup of future IDE processes. Recovery of a surviving test-owned IDE remains part of later IDE lifecycle work.
